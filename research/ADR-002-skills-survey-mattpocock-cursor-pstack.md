## Repo conventions

### mattpocock/skills

Source: `CLAUDE.md`, `.agents/invocation.md`, `.agents/writing-docs.md`, `skills/engineering/README.md`, `README.md`.

- **Layout.** `skills/<bucket>/<name>/SKILL.md` with buckets `engineering/`, `productivity/` (promoted, shipped in the plugin, listed in README and `.claude-plugin/plugin.json`), `misc/`, `in-progress/`, `deprecated/` (not promoted). Each bucket has a `README.md` listing its skills, grouped into **User-invoked** and **Model-invoked** (`CLAUDE.md`).
- **Every skill also carries `agents/openai.yaml`** beside `SKILL.md` for Codex: `interface.display_name`, `interface.short_description`, and for user-invoked skills `policy.allow_implicit_invocation: false` (`.agents/invocation.md`). Example, `skills/productivity/grill-me/agents/openai.yaml`:
  ```yaml
  interface:
    display_name: "Grill Me"
    short_description: "Sharpen a plan through interview"
  policy:
    allow_implicit_invocation: false
  ```
- **The one axis: invocation.** User-invoked = `disable-model-invocation: true` in frontmatter, human-facing description with trigger lists stripped; model-invoked = default, description "keeps rich trigger phrasing ('Use when the user wants…, mentions…, asks for…')". "A user-invoked skill may invoke model-invoked skills, but it can never reach another user-invoked skill." (`.agents/invocation.md`)
- **Dependencies are expressed as `Call the Skill tool with "grilling"`**, never `../other-skill/FILE.md` cross-links and never a bare `/skill` mention. "The Skill tool takes one skill per call. A step that needs two skills is two calls" (`.agents/invocation.md`). CHANGELOG entry #781 removed Claude Code tool names (`Agent`, `subagent_type=Explore`) from sub-agent dispatch so skills stay harness-neutral.
- **Frontmatter keys actually used:** only `name`, `description`, and optionally `disable-model-invocation: true`. No `allowed-tools`, `argument-hint`, `context`, `agent`, or `model` anywhere in the repo.
- **Docs pages** at `docs/<bucket>/<skill>.md`, published as `https://aihero.dev/skills-<name>`, with a fixed frame: `## What it does` (must state the "defining constraint"), `## When to reach for it` (invocation mode + trigger boundary, branches in a table), optional `## Prerequisites`, free-form middle surfacing the "leading word", `## Common questions` (only *observed* questions from issues/changelog/wiki, "the count stays honest to the evidence"), `## It's working if` (checkable without opening SKILL.md), `## Where it fits` (role + neighbours + link to router). (`.agents/writing-docs.md`)
- **Style rule:** "No em-dashes anywhere in this repo's prose" (`CLAUDE.md`). `.changeset/remove-em-dashes-repo-wide.md` and `grilling-remove-em-dashes.md` record the sweep.
- **Router skill** `ask-matt` must be re-synced whenever a skill is added/renamed/removed (`CLAUDE.md`).
- **Domain glossary** `CONTEXT.md` at repo root defines the repo's own terms (Issue tracker, Issue, Decision ticket, Triage role) with `_Avoid_:` synonyms.
- **`.out-of-scope/`** holds declined feature requests with reasoning (e.g. `question-limits.md`: no hard cap on grilling questions; "natural-language steering is the intended control surface, not a numeric limit").
- **Skill-writing theory** lives in `skills/productivity/writing-for-agents/SKILL.md`: context pointers ("The pointer's *wording*, not its target, decides when the agent reaches the material"), two loads (context load vs cognitive load), information hierarchy (in-file step > in-file reference > disclosed reference), completion criteria ("The strongest criteria are both checkable and exhaustive"), leading words ("a compact concept already living in the model's pretraining… *tight*, *red*, *seam*"), negation ("Prompt the **positive**… A prohibition earns its place only as a hard guardrail you cannot phrase positively"), pruning (single source of truth; the environment is a source of truth, docs restating it are a "cache"; hunt "no-ops": "an instruction the model already obeys by default pays load to say nothing").

### cursor/plugins (pstack)

Source: `README.md` (root), `pstack/README.md`, `pstack/.cursor-plugin/plugin.json`, `pstack/skills/poteto-mode/SKILL.md`, `pstack/docs/guide/*.md`.

- **Layout.** Multi-plugin marketplace: each plugin at repo root with `.cursor-plugin/plugin.json` (`"skills": "./skills/"`, `"agents": "./agents/"`, optional `"rules": "./rules/"`), `skills/<name>/SKILL.md`, optional `skills/<name>/references/*.md`, `skills/<name>/scripts/`, `agents/<name>.md` for subagent definitions, `docs/guide/` for human docs.
- **Frontmatter keys used in pstack:** `name`, `description`, `disable-model-invocation: true` (on almost every skill, including `unslop`, `interrogate`, `architect`, `why`, `how`, `blast-radius`, `arena`, `swarm`, `reflect`, `figure-it-out`, all 23 `principle-*` skills). `poteto-mode` additionally uses Cursor-specific keys `mode: true`, `icon: crown`, `color: yellow`, `reminder: ...`. `setup-pstack` is the one skill without `disable-model-invocation`. Agent files use `name`, `description`, and `is_background: true` (`agents/poteto-agent.md`). No `allowed-tools`, `argument-hint`, `context`, `agent`, or `model` frontmatter keys.
- **Descriptions are trigger-phrase driven** even with model invocation disabled: e.g. `interrogate`: `Use for "interrogate", "adversarial review", "multi-model review", "challenge this", "stress test this code", "find blind spots", or "tear this apart".`
- **Hub-and-spoke:** `poteto-mode` is a sticky "mode" skill that matches the task to one of 23 playbooks (`playbooks/*.md`), opens a todo list with the playbook steps "copied in verbatim", and routes to the other skills as steps fire. It inlines an index of 23 `principle-*` skills (one principle each, e.g. `principle-laziness-protocol`, `principle-prove-it-works`) and requires the reply to "name each principle that shaped a decision and the specific choice it changed" (`poteto-mode/SKILL.md`).
- **Multi-model by design.** Skills name explicit model slugs per role (`claude-fable-5-1-thinking-max` for prose/judgment, `grok-4.6-fast-xhigh` for code/explorers, `gpt-5.6-sol-max`, `claude-opus-5-thinking-xhigh` for panels). `setup-pstack` writes `~/.cursor/rules/pstack-models.mdc` (`alwaysApply: true`) with one line per role, e.g. `interrogate reviewers: claude-fable-5-1-thinking-max, gpt-5.6-sol-max, grok-4.6-fast-xhigh, claude-opus-5-thinking-xhigh`; list length sets fan-out count; `inherit-parent` / `auto` mean "run on the parent chat model".
- **Subagent conventions** (`poteto-mode/SKILL.md` "Subagents"): defaults for every `Task` call are `run_in_background: true`, agent mode ("readonly strips MCP"), "file pointers not inlined context", explicit model per role. "You own every subagent's work. Review the diff and write your own summary, don't pass through what it said." "A second opinion is the same prompt against a different model. Agreement is high-signal."
- **Reply style** (`poteto-mode/SKILL.md` "Writing the reply"): short declarative sentences; "No long-dash character anywhere"; no colon as mid-sentence connector (cites `unslop` rule 14); "Frame impact for the consumer and the maintainer"; "Every claim carries its evidence or its label in the same sentence. Measured, inferred, or guess."
- **Skill authoring** (`playbooks/authoring-a-skill.md`): "When in doubt, delete. Keep only prose that changes a decision. Tell it to do the thing and skip the reason… Delegate to other skills by path. Don't restate." Validate `name`/`description`, referenced files exist, cross-skill links resolve.
- **Philosophy differences vs mattpocock:** pstack README "why are there no planning skills?": "i don't believe in planning. the best spec is code." `principle-never-block-on-the-human`: "Proceed, present the result, let the human course-correct after the fact; reserve confirmation for irreversible actions." Where mattpocock grills the human, pstack classifies a fork: "If the answer is a fact you could observe by running something… it is not the human's to answer. Sketch it via the Prototype playbook" (`poteto-mode/SKILL.md`).

## mattpocock/skills: skill by skill

### `grilling` (the interview primitive)

- Path: `skills/productivity/grilling/SKILL.md`. Frontmatter: `name: grilling`, `description: Grill the user relentlessly about a plan, decision, or idea. Use when the user wants to stress-test their thinking, or uses any 'grill' trigger phrases.` Model-invoked (no `disable-model-invocation`). `agents/openai.yaml`: display "Grilling", short "Stress-test thinking a round of questions at a time".
- Whole body is ~20 lines. Workflow, near-verbatim:
  1. "Interview the user relentlessly until you reach a shared understanding. Map this as a **design tree**: every decision branches into the decisions that hang off it."
  2. "Work the tree in **rounds**. The **frontier** is every decision whose prerequisites are already settled: the questions you can ask *now* without guessing at answers you haven't heard yet. Ask the whole frontier in one round: number each question and give your recommended answer. Then wait for the user's answers before the next round."
  3. Round format (verbatim):
     ```
     ❓ **Q1** - **<question title>**: <question body, might be multiple paragraphs, including multiple choices>

     ➡️ <your recommended answer>

     ---

     ❓ **Q2** - **<question title>**: ...

     ➡️ <your recommended answer>
     ```
     (The `---` separator between questions was added by changeset `grilling-add-hr-between-questions.md`.)
  4. "Each round the user answers reshapes the tree… A question whose answer depends on another question still open in this round belongs to a *later* round, not this one."
  5. Facts vs decisions: "Finding *facts* is your job, never the user's. When a frontier question needs a fact from the environment (filesystem, tools, etc.), dispatch a sub-agent to find it; don't ask the user for anything you could look up yourself. Don't block on it: a running exploration is an unsettled prerequisite, so only the questions downstream of it wait for the sub-agent to report; ask the rest of the frontier now. The *decisions* are the user's: put each to them and wait."
  6. Termination: "The session is done when the frontier is empty: every branch of the design tree visited, nothing left silently assumed. Do not act on it until the user confirms you have reached a shared understanding."
- Subagents: yes, dispatched for facts, non-blocking (harness-neutral wording, no tool named).
- History (CHANGELOG): #593 reworked from one-question-at-a-time to rounds ("Same 13 questions land in ~3 rounds instead of 13"); #464 split facts from decisions because the old "explore the codebase instead" line "read as license to answer *decisions* autonomously"; #532 generalised wording beyond software. Opt-out documented in `docs/productivity/grilling.md`: add `When grilling, ask one question at a time.` to global `CLAUDE.md`. Hard question caps are explicitly out of scope (`.out-of-scope/question-limits.md`).
- Known rough edges (`docs/productivity/grilling.md`): "the frontier is the agent's judgement, not a computed graph"; weaker models "collapse 'interview until shared understanding' into a couple of questions and an outline"; a skill that names another skill "does not reliably cause that skill to load".

### `grill-with-docs` (+ `domain-modeling`)

- Path: `skills/engineering/grill-with-docs/SKILL.md`. Frontmatter: `name: grill-with-docs`, `description: A relentless interview to sharpen a plan or design, which also creates docs (ADR's and glossary) as we go.`, `disable-model-invocation: true`. Body is one line: `Call the Skill tool twice, for "grilling" and "domain-modeling".`
- `domain-modeling` (`skills/engineering/domain-modeling/SKILL.md`, model-invoked, description "Build and sharpen a project's domain model. Use when discussing codebase terminology, writing or editing a CONTEXT.md, or recording or editing an ADR.") supplies the writing discipline:
  - File structure: single-context repo has `CONTEXT.md` at root and `docs/adr/NNNN-slug.md`; multi-context repo has `CONTEXT-MAP.md` at root pointing at per-context `CONTEXT.md` + `docs/adr/`. "Create files lazily: only when you have something to write."
  - During the session: **Challenge against the glossary** ("Your glossary defines 'cancellation' as X, but you seem to mean Y. Which is it?"); **Sharpen fuzzy language** ("You're saying 'account': do you mean the Customer or the User?"); **Discuss concrete scenarios** (invent edge-case scenarios); **Cross-reference with code** ("Your code cancels entire Orders, but you just said partial cancellation is possible. Which is right?"); **Update CONTEXT.md inline** ("Don't batch these up"); "`CONTEXT.md` should be totally devoid of implementation details… It is a glossary and nothing else."
  - **Offer ADRs sparingly**, only when all three hold: "1. **Hard to reverse**… 2. **Surprising without context**… 3. **The result of a real trade-off**". Formats in `CONTEXT-FORMAT.md` and `ADR-FORMAT.md` (same folder).
- Known issues (`docs/engineering/grill-with-docs.md`): when run inside another orchestration layer "the file-writing half is reported to silently not happen"; partial loading ("`grilling` loads, `domain-modeling` does not"); most decisions "exist only in the context window" because the glossary is not a spec and ADRs are gated, so hand the same conversation to `to-spec`.

### `code-review`

- Path: `skills/engineering/code-review/SKILL.md`. Frontmatter: `name: code-review`, `description: "Review the changes since a fixed point (commit, branch, tag, or merge-base) along two axes: Standards (does the code follow this repo's documented coding standards?) and Spec (does the code match what the originating issue/spec asked for?). Runs both reviews in parallel sub-agents and reports them side by side. Use when the user wants to review a branch, a PR, work-in-progress changes, or asks to \"review since X\"."` Model-invoked. Precondition: `docs/agents/issue-tracker.md` (written by `/setup-matt-pocock-skills`); if missing, tell the user to run setup.
- Workflow:
  1. **Pin the fixed point.** If not supplied, ask. `git diff <fixed-point>...HEAD` (three-dot, merge-base) and `git log <fixed-point>..HEAD --oneline`. "Before going further, confirm the fixed point resolves (`git rev-parse <fixed-point>`) and the diff is non-empty. A bad ref or empty diff should fail here, not inside two parallel sub-agents."
  2. **Identify the spec source**, in order: issue refs in commit messages (`#123`, `Closes #45`, GitLab `!67`) fetched via the issue-tracker doc; a path the user passed; a spec under `docs/`, `specs/`, `.scratch/` matching branch/feature; else ask, and if none exists the Spec sub-agent "will skip and report 'no spec available'".
  3. **Identify the standards sources** (`CODING_STANDARDS.md`, `CONTRIBUTING.md`, etc.) plus the always-on **smell baseline**. Two binding rules: "**The repo overrides.** A documented repo standard always wins… **Always a judgement call.** Each smell is a labelled heuristic ('possible Feature Envy'), never a hard violation… skip anything tooling already enforces."
     The 12 Fowler smells, verbatim (*what it is* → *how to fix*):
     - **Mysterious Name**: a function, variable, or type whose name doesn't reveal what it does or holds. → rename it; if no honest name comes, the design's murky.
     - **Duplicated Code**: the same logic shape appears in more than one hunk or file in the change. → extract the shared shape, call it from both.
     - **Feature Envy**: a method that reaches into another object's data more than its own. → move the method onto the data it envies.
     - **Data Clumps**: the same few fields or params keep travelling together (a type wanting to be born). → bundle them into one type, pass that.
     - **Primitive Obsession**: a primitive or string standing in for a domain concept that deserves its own type. → give the concept its own small type.
     - **Repeated Switches**: the same `switch`/`if`-cascade on the same type recurs across the change. → replace with polymorphism, or one map both sites share.
     - **Shotgun Surgery**: one logical change forces scattered edits across many files in the diff. → gather what changes together into one module.
     - **Divergent Change**: one file or module is edited for several unrelated reasons. → split so each module changes for one reason.
     - **Speculative Generality**: abstraction, parameters, or hooks added for needs the spec doesn't have. → delete it; inline back until a real need shows.
     - **Message Chains**: long `a.b().c().d()` navigation the caller shouldn't depend on. → hide the walk behind one method on the first object.
     - **Middle Man**: a class or function that mostly just delegates onward. → cut it, call the real target direct.
     - **Refused Bequest**: a subclass or implementer that ignores or overrides most of what it inherits. → drop the inheritance, use composition.
  4. **Spawn both sub-agents in parallel.** Standards brief includes diff command, commit list, standards files, "**plus the smell baseline from step 3 pasted in full** (the sub-agent has no other access to it)", and: "Report, per file/hunk where relevant, (a) every place the diff violates a documented standard: cite the standard (file + the rule); and (b) any baseline smell you spot: name it and quote the hunk. Distinguish hard violations from judgement calls… Skip anything tooling enforces. Under 400 words." Spec brief: "Report: (a) requirements the spec asked for that are missing or partial; (b) behaviour in the diff that wasn't asked for (scope creep); (c) requirements that look implemented but where the implementation looks wrong. Quote the spec line for each finding. Under 400 words."

### `prototype`

- Path: `skills/engineering/prototype/SKILL.md` + `LOGIC.md` + `UI.md`. Frontmatter: `name: prototype`, `description: Build a throwaway prototype to answer a design question. - `LOGIC.md` (single shareable HTML demo): 1. State the question at the top of the demo, visibly. 2. Isolate the logic in a portable pure module in one `<script>` block (pure reducer `(state, action) => state`, explicit state machine, pure functions over a data type, or a class with a clear method surface; "Keep it pure: no DOM, no `document`, no button handlers reaching inside it"). 3. Build the HTML file: "One file, plain HTML/CSS/JS: no framework, no bundler, no server"; written for a non-developer in **domain language**; layout top-to-bottom: title + one-line explanation, **Current state** panel (labelled fields, not raw JSON, re-rendered after every click), **Free-play buttons** (one per action), **Guided walkthroughs** (tabs, one scenario each, plain-language description, ordered real buttons, "Starting a walkthrough resets to a known initial state"); scenarios = happy path, a tricky edge case, "an attempt at something that should be illegal"; "Keep it beautiful but restrained… one accent colour. ### `unslop`

- Path: `pstack/skills/unslop/SKILL.md`. Frontmatter: `name: unslop`, `description: Cut AI tells from any writing. Must always apply.`, `disable-model-invocation: true`. No supporting files, no subagents.
- Process (verbatim): "1. Scan for the patterns below. 2. Rewrite. Preserve meaning, match intended tone. 3. Self-audit: 'What makes this obviously AI generated?' Fix remaining tells."
- "Rule numbers are stable ids that other skills cite. A removed rule leaves a gap." (Numbers 1, 2, 4, 6, 21 are absent.) Other skills cite them: `poteto-mode` cites "unslop rule 14"; `technical-writing` says to propose new offenders "as an addition to `unslop`'s abstract-metaphor rule".
- Full rule list (verbatim, grouped as in the file):
  - **Content.** 3. **Superficial -ing phrases.** "highlighting...", "ensuring...", "reflecting...", "showcasing...", "fostering...". Delete or expand with real sources. 5. **Vague attributions.** "Experts believe", "Industry reports suggest", "Some critics argue". Name the source or delete.
  - **Language.** 7. **AI vocabulary.** Additionally, crucial, delve, enduring, enhance, fostering, garner, interplay, intricate, landscape (abstract), pivotal, showcase, tapestry (abstract), testament, underscore, vibrant. Replace with plain words. 8. **Fancy ways to say "is".** "serves as", "stands as", "boasts", "features". Just say "is" or "has". 9. **"Not just X, but Y."** State the point directly instead. 10. **Rule of three.** Forcing ideas into groups of three. Use the natural number. 11. **Synonym cycling.** Protagonist, main character, central figure, hero all in one paragraph. Pick one, repeat it. 12. **False ranges.** "from X to Y" where X and Y aren't on a meaningful scale. List topics directly.
  - **Style.** 13. **Em dash overuse.** Avoid em dashes entirely. Use periods or commas only (no parentheses, no en dashes, no hyphen-as-dash substitutes). If a thought needs separation, end the sentence or use a comma. 14. **Colon overuse.** Colons are fine before a list or example. Not as mid-sentence connectors. [example given] 15. **Boldface overuse.** Don't bold every proper noun or acronym. 16. **Inline-header lists.** The tell is a bold label and colon that restates the line: "**Performance:** Performance improved...". Convert those to prose. A bold lead-in that ends in a period, names the item, and is followed by genuinely new detail ("**Schema in TypeScript.** Tables live in one file.") is fine, not a tell. 17. **Title case headings.** Use sentence case. 18. **Decorative emojis.** Remove from headings and bullets. 19. **Curly quotes.** Replace with straight quotes.
  - **Communication artifacts.** 20. **Chatbot phrases.** "I hope this helps!", "Let me know if...", "Of course!", "Certainly!", "Found the smoking gun!" Remove. 22. **Sycophantic tone.** "Great question! You're absolutely right!" Respond directly.
  - **Filler.** 23. **Filler phrases.** "In order to" becomes "To". "Due to the fact that" becomes "Because". "It is important to note that" gets deleted. 24. **Excessive hedging.** "could potentially possibly be argued that it might" becomes "may". 25. **Generic conclusions.** "The future looks bright." State specific plans or facts.
  - **Jargon.** 26. **Abstract metaphor nouns.** Substrate, wedge, vector, locus, vantage, nexus, primitive (as noun), harness (as metaphor), surface (as in "API surface"), bedrock, scaffolding (as metaphor), modality, paradigm, gold-plating, ratchet (as metaphor), evacuate (for moving code), endgame, north star, flywheel. These read as technical but usually have a plainer concrete word. "Substrate" becomes "base". "Wedge in" becomes "add". "Vector" becomes "way" or "method". "Gold-plating" becomes "more than the job needs". "Ratchet" becomes the mechanism's real name or "a limit that only tightens". "Evacuate" becomes "move out". "Endgame" becomes "the last phase". Pick the concrete word.
  - **Plain speech.** 27. **Say what it does, not how it feels.** "the database stays close at hand", "SQL you can read", "types that follow your schema" name a feeling. The fix names the mechanism or a number: "`.toSQL()` returns the exact string sent to the database", "a column rename fails the build". Ask what the sentence tells the reader to do or know, then write that. If you can't restate it as a concrete instruction, fact, or number, cut it. One more check: if the sentence could appear unchanged in another project's docs, it says nothing about this one. Cut it. 28. **Shorten or split dense sentences.** If the reader has to backtrack to parse a sentence, break it in two or drop clauses. One idea per sentence. 29. **Active voice.** Prefer it. Catch "is/are/was/were + past participle" and name the actor: "queries are validated" becomes "the compiler validates queries"… Passive is fine only when the actor is unknown or genuinely doesn't matter. 30. **Cut adverbs, or use a stronger verb.** "runs quickly" becomes "is fast" or the number. "significantly improves" becomes the measured delta. An adverb propping up a weak verb means the verb is wrong. 31. **Prefer the plain word.** "utilize" becomes "use", "leverage" becomes "use", "facilitate" becomes "help", "numerous" becomes "many", "in the event that" becomes "if". The fancier synonym is rarely clearer. 32. **Mannered prose.** Metaphor or flourish where a literal phrase exists: aphorisms ("wire it or delete it"), rhetorical fragments for effect, personified code ("the plan holds it"), figurative verbs ("rides along", "stands on"), stock framing phrases. "A dial worth turning" becomes "a parameter worth varying". Say what you mean. Rule 26 covers the metaphor nouns. 33. **Over-compression.** Dropped articles, verbless fragments, symbol-speak, and abbreviations that make the reader decode instead of read. "Parser rejects bad date → exit 2, no write" becomes "The parser rejects a bad date, exits with code 2, and writes nothing." Write whole sentences with their articles and verbs, and spell out arrows and abbreviations.
- Related: `cursor-team-kit/skills/deslop/SKILL.md` is the *code* counterpart (model-invoked; "Check the diff against main and remove AI-generated slop": unnecessary comments, abnormal defensive checks/try-catch, `any` casts, deep nesting; guardrails: "Keep behavior unchanged unless fixing a clear bug", "minimal, focused edits", summary 1-3 sentences). `poteto-mode` routes "Before commit → the `deslop` skill" and "Any prose surface → the **unslop** skill". `pstack/skills/bro/SKILL.md` is a one-line "Restate the last message in plain human language, with no jargon."

### `interrogate` (multi-model adversarial code review)

Filtering principles (verbatim headings): **Nitpick Gravity** ("If a reviewer's findings are all nits and style preferences, the code is probably fine. Say so."), **Hypothetical vs. Actual** ("Trace the call site. - Subagents: N read-only reviewers in parallel, each on a different model. Ladder in `docs/guide/04-design.md`: "A small, finished change you're unsure about needs `/interrogate` alone… A contested design that's expensive to reverse gets `/architect`, then `/interrogate` before shipping."

### `blast-radius`

- Path: `pstack/skills/blast-radius/SKILL.md`. Frontmatter: `name: blast-radius`, `description: "Find what a change could break somewhere else before it ships, beyond the diff, and prove the one fact it's safe because of by running real code instead of writing it up. Use for 'blast radius of X', 'what could this break', or reviewing a small diff you don't trust."`, `disable-model-invocation: true`.
- "Listing the callers is not the job. The agent can grep those in a second. The job is the breakage grep won't show you." "A blast-radius writeup that sounds right is worthless… Find the one or two facts the whole thing depends on and prove them by running code."
- Evidence ladder (verbatim): "1. You said so. Worthless on its own. 2. You pointed at the line. A real `file:line`, or the library's own source. 3. You showed the bad case can't happen. - Steps: 1. Read the change (use `why` step 2 to pull PR/commits). 2. "Find the one fact it's safe because of." 3. ### `architect` (design before code) + references

- Path: `pstack/skills/architect/SKILL.md`. Frontmatter: `name: architect`, `description: "Sketch types, signatures, and module structure before code, then stay in the loop while implementation fills in. Use for /architect, 'architect this', 'design this', or non-trivial work where jumping to code would lock in the wrong shape."`, `disable-model-invocation: true`. References: `design-red-flags.md`, `rationale-template.md`, `runner-prompt.md`.
- Phases (todo list opened first: Ground, Sketch, Agree, Implement, Scrap):
  - **A. Ground**: run the `how` skill over touched subsystems ("Naming a file isn't grounding. Produce the traced model"); run `why` if the design redefines ownership/layering. Skip only for greenfield.
  - **B. Sketch**: run `arena` with `references/runner-prompt.md` as each runner's prompt (default runners `claude-fable-5-1-thinking-max`, `gpt-5.6-sol-max`, `grok-4.6-fast-xhigh`, `claude-opus-5-thinking-xhigh`). "Design it twice. Require at least two structurally distinct candidates before synthesis… Whole-shape alternatives, not point fixes inside one shape." Screen every candidate against `design-red-flags.md`. "Compare viable candidates on interface depth. Prefer the design that hides more complexity behind a smaller, simpler public surface."
  - **C. Agree (opt-in)**: "Default: proceed directly to implementation with the synthesized design. No human checkpoint." Opt in with "/architect with checkpoint". Human pushback "is Phase A evidence. Re-ground and re-run Phase B."
  - **D. Implement against the sketch**: "Replace `not implemented` bodies with code… The synthesized sketch is the contract. Deviations from the sketch are signal worth surfacing, not friction to absorb silently."
  - **E. Scrap when the architecture is wrong**: "The signal is a *pattern*, not single instances. Tells: The same shape of workaround appearing repeatedly… Multiple unrelated edge cases that all need special-case branches. Types that need escape hatches (`any`, casts, optional fields always set in practice) to compile. The 'we need a lock' reflex when the sketch said the state wasn't shared. Callers having to know the abstraction's internal rules… Two or more independent Phase D deviations of the same shape." When scrapping: re-run `how`, redesign from first principles, "Subtract before adding… The new sketch should be smaller than the old one before it grows", re-run arena.
  - **Outputs**: "The caller's usage is written first and the type sketch derived from it."
- `references/design-red-flags.md` (Ousterhout-derived, verbatim headings + gist): **Shallow module** ("Do not confuse a deep module with a deep call chain"; signs: callers coordinate several methods for one operation; public options expose internal stages; learning the interface doesn't save learning the implementation); **Information leakage** ("Public re-exports of transport or wire types are leakage. Parse external data into domain types behind the interface"); **Temporal decomposition** ("organizes modules by execution order instead of the knowledge they own… Group code around domain knowledge and ownership"); **Pass-through method** ("Keep a forwarding boundary only when it adds policy, adaptation, or a distinct abstraction").
- `references/rationale-template.md` (one page): `## Problem`, `## Usage (caller's view)` ("Write this first, before the type sketch… The caller's experience is the spec. The types serve it."), `## Shape` ("Data structures first… Cite the principle behind each decision (e.g., `per boundary-discipline`)"), `## Synthesis decision` (filled by arena), `## Tradeoffs accepted` ("we accept X in exchange for Y"), `## Alternatives considered` ("Required… Avoid listing flavors of the same shape"), `## Open questions and risks` ("Phrase as questions"), `## Next implementation step`.
- `references/runner-prompt.md` discipline list (verbatim leads): "Caller's usage first… Data structures first… If the answer is 'we'll add a map / index / cache later,' the structure is wrong… Interface depth… Shared state: if two actors might both write, ask 'what happens?'… Make boundaries visible. `not implemented` errors for bodies, `// TODO` pseudocode for tricky logic… Encode invariants in types: hard-to-misuse types > runtime checks > prose comments… Validate at boundaries, trust types inside… Single source of truth per invariant. Derive instead of sync… Idempotent state transitions… Short call chains. If tracing the flow needs more than three files, flatten the hierarchy." And: "Don't hedge against the others. Differences between candidates are the signal used to pick a base and graft. Converging on a safe-looking middle defeats the exploration."

### `arena` and `swarm` (fan-out primitives)

- `arena` (`pstack/skills/arena/SKILL.md`, `disable-model-invocation: true`, description "Spawn N parallel candidates at the same task, pick a base, graft the strongest parts of the losers into it…"). Phases: **Frame** (state the artifact; "Derive the rubric… 3-6 concrete gradeable criteria. The rubric is the picker's tool in Phase D. Candidates only see the task."; pick runners from config or the 4 defaults; "Same model N times when the work is generation-bound rather than judgment-sensitive"; each candidate gets its own worktree or `/tmp/arena-<slug>/candidate-<n>/`). **Fan out** (all N in one message, `run_in_background: true`, each produces artifact + rationale naming rejected alternatives; dropouts noted). **Cross-judge** (one readonly judge "Prefer a different model family from the parent's", scores criterion by criterion, recommends a base; runs after candidates finish). **Pick** ("Read every candidate end to end before picking… Score… criterion by criterion, not on holistic feel… Disagreement [with the judge] means one of you is biased or the rubric was ambiguous"; tie-break "Prefer the cleaner boundary or smaller API"). **Graft** ("The signal is usually one or two things per candidate, not most of it… Fold each graft in by hand"; "When N candidates converge on the same shape, that is a strong agreement signal… When N candidates wildly diverge, Phase A was under-specified. Reframe and re-run rather than averaging"). **Verify**. Output: one artifact + one synthesis note (base, grafts with source, rejections, dropouts, verification).
- `swarm` (`pstack/skills/swarm/SKILL.md`): coverage/race variant. Frame (done predicate; shape = partition slices, race identical briefs with `first pass` / `rank all` / `best-of`, or mix; N; model), Fan out (`environment: "cloud"`, `run_in_background: true`; "Every brief stands alone… Reports use `PASS`, `ISSUES`, or `BLOCKED` with evidence"), Aggregate ("Do not paste raw worker dumps"), Report (compact table + issue one-liners + gaps).

### `why` (historical research) + `how` (codebase walkthrough)

- `why` (`pstack/skills/why/SKILL.md`, `disable-model-invocation: true`; description lists triggers "why does X work this way", "why we picked Y", design rationale, regressions, postmortems, data-backed thresholds; "Use how for runtime behavior"). References: `epistemics.md`, `investigator-prompt.md`, `synthesizer-prompt.md`, `source-playbook.md`, `sources/{code-archaeology,linear,notion,slack,datadog,sentry,databricks,incident-postmortem}.md`.
  - Steps: 1. Parse target + question (guess from context if vague, state interpretation). 2. **Code anchor** built inline: `git blame -L`, `git log --follow -p`, `git log --oneline -20 -- <file>`, extract `(#1234)` PR numbers, `gh pr view <n> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews`. 3. **Discovery**: list available MCPs, map each to one of 7 evidence categories (source control, issue tracker, long-form docs, real-time chat, infra observability, error tracking, analytics warehouse); "Aim for a complete **coverage map**, not a minimal one. Document the null, don't skip the search." Spawn one investigator per category with a matching MCP, all in one message, `readonly: false` because "readonly/Ask mode… strips MCP access". Each gets the base prompt + the category playbook + `incident-postmortem.md` if the code looks defensive + the anchor + the question. Skipping a category requires "an **explicit, written justification**" (no MCP, or "provably irrelevant"). 4. **Synthesize** via one synthesizer subagent with the epistemics framework. 5. Present "but **do not rewrite the confidence language**". Optional tail: if the question precedes a change, "convert the lineage findings into a Preserve / Change / Avoid / Risk constraint set".
  - `investigator-prompt.md`: "Quote, don't paraphrase… Go wide before going deep… Track what you searched, not just what you found… Resist the story. If three pieces of evidence line up neatly and a fourth contradicts them, the contradiction is the most interesting finding… Consider the counterfactual… Never invent." Stay inside the assigned source; cross-source leads go under "Additional Leads". Output: Source / What I Searched / Direct Evidence Found / Indirect / Contradictions / Gaps / Additional Leads. "Don't confuse mechanics with motivation… Don't infer intent from code style… No silent substitutions."
  - `epistemics.md` confidence tiers (verbatim names): **Direct** ("Something an author actually *wrote* that says why"; phrasing confident, cite), **Supported** (multiple indirect pieces converge), **Inferred** (hedged: "appears", "likely", "suggests"; make the chain explicit), **Speculative** ("One possibility is X, but we have no direct evidence"), **Unknown** ("We searched X, Y, and Z and found no evidence"). Words that carry confidence: "because", "the reason is", "was designed to", "fixes", "the team decided". Words to avoid: "obviously", "clearly", "of course", "just", "I think". "The Sycophancy Trap": a user's embedded hypothesis "is a prompt for investigation, not a conclusion to validate." "Never cite code as evidence for its own intent."
  - `synthesizer-prompt.md` output: The Question / The Code in Question / What We Found (`[Direct]`, `[Supported]` bullets with citations) / What We Can Reasonably Infer (`[Inferred]`) / Competing Hypotheses / What We Don't Know / Sources Consulted (one line per category, including "Not searched. No matching MCP available") / Confidence Summary; plus a 7-item quality checklist ("Does the 'What We Don't Know' section exist and name specific gaps? If it's empty or missing, be suspicious").
- `how` (`pstack/skills/how/SKILL.md`, `disable-model-invocation: true`; description covers "how does X work", walkthroughs before changing, placement/ownership/layering questions). Step 1 assess complexity: **Simple** → one explainer subagent explores and explains; **Complex** → "Decompose the question into 2 to 4 exploration angles", spawn read-only explorers (default model `grok-4.6-fast-xhigh`) in one message, then one explainer (default `claude-fable-5-1-thinking-max`). "When in doubt, take the simple path." Explorer output (`explorer-prompt.md`): Components Found / Flow / Files Read / Boundaries / Non-Obvious Things / Open Questions; "Don't guess from names. Read the code." Explainer output (`explainer-prompt.md`): Overview / Key Concepts / How It Works (prose, mermaid or ASCII diagram only when it clarifies) / Where Things Live / Gotchas; style "Say 'the `UserService` calls `AuthClient.refresh()`' not 'the service delegates to the client'".
- The `investigation` playbook (`playbooks/investigation.md`) is pstack's "research" entry: read-only, route through `how` (+ `why` for motivation), produce the `how`-shaped output or "a recommendation with a tradeoffs table", apply `unslop`, "Push back if the premise is wrong."

### Prototype playbook + `principle-exhaust-the-design-space`

### `code-review` (new skill; merge the two designs)

- Borrow pstack's `why` epistemics for the output format: tag claims `[Direct]` / `[Supported]` / `[Inferred]` / `[Speculative]`, add a "What We Don't Know" and "Sources Consulted" section, forbid "obviously/clearly/just", and treat the user's embedded hypothesis "as a candidate, not a conclusion". Borrow the investigator rules "Quote, don't paraphrase", "Track what you searched, not just what you found", "Resist the story".
- Consider a `why` sub-mode (git archaeology: `git blame -L`, `git log --follow -p`, PR numbers from `(#1234)`, `gh pr view … --json …`) since that anchor-building recipe is harness-neutral and cheap.
- Consider a `how` sibling (2-4 read-only explorers → one explainer, output Overview / Key Concepts / How It Works / Where Things Live / Gotchas) as the "understand before changing" step ai-toolbox's `planner` could call.

### `prototype` (new skill; port mattpocock, add pstack's evidence step)

- Port `SKILL.md` + `LOGIC.md` + `UI.md` structure nearly as-is (MIT): question-first branch choice, the six shared rules, the single-file HTML logic demo (pure module in one `<script>`, domain-language labels, state panel + free-play + tabbed walkthroughs with reset), the UI variants (default 3, cap 5, "structurally different… not just different colours", sub-shape A on the existing route, `?variant=` + floating bar + arrow keys + `NODE_ENV` gate), the anti-pattern lists, and "capture it as a primary source on a `prototype/<name>` branch".

- Add pstack's fork classifier as the trigger sentence: if a "which approach" question can be answered by running something, prototype it instead of asking. This is the bridge between a grilling skill and a prototype skill.
- Add the naming caveat from mattpocock's docs: don't recommend `/prototype` when the design is settled; the next step is implementation.

### Architecture review (new skill; two complementary shapes)

- **Survey shape** (from `improve-codebase-architecture`): YAGNI scoping via recent `git log` hot spots or a user-named direction; organic exploration by a sub-agent looking for shallow modules, no-locality helpers, seam leaks, untestable code; the **deletion test**; candidate cards with Files / Problem / Solution / Benefits in locality+leverage terms / Before-After diagram / `Strong` `Worth exploring` `Speculative` badge / dependency category; Top recommendation; stop and ask "Which of these would you like to explore?"; offer an ADR when a candidate is rejected for a durable reason. Ship the HTML report (`HTML-REPORT.md` scaffold) but also offer a Markdown-only mode, since the CDN report is the most reported failure.
- **Design shape** (from pstack `architect`): ground first (run the `how`-style walkthrough), sketch N structurally distinct candidates in parallel (mattpocock's DESIGN-IT-TWICE constraints "minimize the interface / maximise flexibility / optimise for the common caller / ports & adapters" are a good default set of 3-4 briefs), screen each against the four **design red flags** (shallow module, information leakage, temporal decomposition, pass-through method), compare on interface depth, write a one-page rationale (`rationale-template.md` sections, "Usage (caller's view)" written first), then implement against a `not implemented` sketch and watch for the **scrap pattern** (repeated workaround shape, escape-hatch types, "we need a lock" reflex).
- Adopt `codebase-design` as a shared vocabulary skill (module, interface, depth, seam, adapter, leverage, locality, with `_Avoid_` lists and the four principles) so the review, the design, and ai-toolbox's existing `architect` persona speak one language. Also port `DEEPENING.md`'s four dependency categories and "replace, don't layer" testing rule.
- The ai-toolbox `architect` persona currently means "orchestrator"; a new design-review skill should use a different name (e.g. `design-review` or `deepen`) to avoid the name clash mattpocock's docs warn about with `code-review`.

Include `CONTEXT-FORMAT.md` and `ADR-FORMAT.md` from `skills/engineering/domain-modeling/`.

### `resolve-merge-conflicts` (new skill; merge both)

- Base on mattpocock's five steps (state → primary sources per side → resolve by intent, preserve both, "Do **not** invent new behaviour", never `--abort` → discover and run typecheck/tests/format → finish incl. `rebase --continue` until done).

- Split skills into **user-invoked** (`disable-model-invocation: true`, human-facing description) vs **model-invoked** (trigger-rich description), and express dependencies as `Call the Skill tool with "<name>"`, one skill per call, never a bare `/name` (mattpocock `.agents/invocation.md`). ## Figma MCP server (official docs)

Verified 2026-09-16 against Figma first-party pages only (help.figma.com, developers.figma.com, figma.com/blog, github.com/figma). Where a claim could not be found on a first-party page, it is marked as such.

### 1. Name, endpoints, plans

- **Current name: "Figma MCP server."** Every current page uses that name (e.g. https://help.figma.com/hc/en-us/articles/32132100833559-Guide-to-the-Figma-MCP-server, https://developers.figma.com/docs/figma-mcp-server/). The launch post was titled "Introducing our Dev Mode MCP server" (June 4, 2025, https://www.figma.com/blog/introducing-figma-mcp-server/) and said it was "available with any Dev or Full seat"; the FAQ and guide no longer use "Dev Mode MCP server". Remote access was announced September 23, 2025: "Now the Figma MCP server supports remote access" (https://www.figma.com/blog/design-context-everywhere-you-build/).
- **Remote endpoint:** `https://mcp.figma.com/mcp`, OAuth in the browser; "Figma strongly recommends using the remote version… provides the broadest set of features" (https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/, https://help.figma.com/hc/en-us/articles/39889260656407-Cursor-and-Figma-Set-up-the-MCP-server).
- **Desktop endpoint:** `http://127.0.0.1:3845/mcp`, enabled in the desktop app: "toggle to Dev Mode or use the keyboard shortcut Shift+D. In the MCP server section of the inspect panel, click Enable desktop MCP server." Provided "for some specific organization and enterprise use cases" and required for Figma for Government (https://developers.figma.com/docs/figma-mcp-server/local-server-installation/). No `/sse` endpoint is documented on that page.
- **Plans/seats:** "The remote server is available on all seats and plans. The desktop server is available on a Dev or Full seat for all paid plans." (guide article above; https://developers.figma.com/docs/figma-mcp-server/rate-limits-access/). Tool-call limits by plan/seat (rate-limits page, verbatim): Starter View/Collab "Up to 20/month"; Starter Dev/Full "Up to 200/day 10/min"; Professional View/Collab "Up to 6/month"; Professional Dev/Full "Up to 200/day 15/min"; Organization View/Collab "Up to 6/month"; Organization Dev/Full "Up to 600/day 20/min"; Enterprise all seats "Up to 600/day 20/min"; Education = Professional Dev/Full. Exempt from limits: `add_code_connect_map`, `create_new_file`, `whoami`. Writing: "A Full Seat is required to write to Figma files outside of drafts. Dev Seats get read-only access outside of their drafts." and "This will eventually be a usage-based paid feature, but is currently available for free during the beta period." (https://help.figma.com/hc/en-us/articles/39252411778583-Figma-MCP-server-FAQs).

### 2. Tools exposed (from https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)

Read tools (`*` = remote only): `get_design_context` ("Design context for a layer or selection"; nodeId or selection; default output React + Tailwind, customizable by prompt; "the default entry point: the other tools in this group are either inputs to it, or fallbacks when a selection is too large or you need a specific asset format"), `get_metadata` ("Sparse XML outline of a selection"), `get_screenshot` ("Screenshot of a selection", optional `enableBase64Response`), `get_variable_defs` ("Variables and styles used in a selection"), `get_code_connect_map` ("Retrieves node ID to code component mappings"), `get_code_connect_suggestions` (Figma-prompted), `get_context_for_code_connect`*, `get_figjam` ("Converts FigJam diagrams to XML"), `get_motion_context` ("Keyframe animation data and code snippets"), `download_assets`* ("Downloads exports and original source images"), `get_libraries`*, `search_design_system`* ("Searches libraries for components, variables, styles"), `list_generative_plugins`*, `get_generative_plugin`*, `list_shaders`, `list_file_shaders`*, `get_shader`, `whoami`*.

Write tools: `use_figma`* ("General-purpose create, edit, and inspect"; runs JavaScript against the Plugin API; Figma Design only per https://developers.figma.com/docs/figma-mcp-server/write-to-canvas/), `generate_figma_design`* ("Generates design layers from interfaces", the code-to-canvas tool), `generate_diagram`* ("Generates a FigJam diagram from Mermaid" or natural language), `create_new_file`* ("Creates a blank Design, FigJam, or Slides file"), `upload_assets`*, `add_code_connect_map`, `send_code_connect_mappings` (Figma-prompted), `create_generative_plugin`*, `update_generative_plugin`*, `create_shader`*, `update_shader`*. Plugin/shader writes require the `figma-generative-plugins` / `figma-shaders` skills ("mandatory prerequisites, not suggestions", https://developers.figma.com/docs/figma-mcp-server/generative-plugins-and-shaders/).

Weave tools (`weave_list_tools`, `weave_get_tool_inputs`, `weave_upload_asset`, `weave_run_tool`, `weave_get_tool_run_output`, `weave_cancel_tool_run`) require a paid Weave account. One MCP prompt: `create_design_system_rules` ("Creates a rule file providing agents context to translate designs into high-quality code"); "not all clients support" MCP prompts. Make files are exposed through the MCP *resources* capability, not a tool (https://developers.figma.com/docs/figma-mcp-server/bringing-make-context-to-your-agent/).

Renames: the tools page states `list_shaders` and `get_shader` "replace deprecated `list_shader_effects`, `list_shader_fills`, `get_shader_effect`, `get_shader_fill`". **`get_code` → `get_design_context`: not verified on a first-party page.** The launch blog names only a "Code tool", "Image tool" and "Variable definitions tool"; the guide, FAQ, tools page and developer-platform updates page contain no "get_code" or "renamed" string. The old name survives only in Figma community forum thread titles (forum.figma.com), which are not first-party documentation.

### 4. Documented prompting best practices

- **Tool order** (guide article): run `get_design_context` first; if the response is too large or truncated, run `get_metadata` for the node map and re-fetch only the needed nodes; run `get_screenshot` for a visual reference ("a screenshot combined with Figma's code outputs performs better than either on their own"); only then `download_assets` and implement.
- **Selection vs link:** with the remote server, "Right-click a frame or layer in Figma and select Copy link to selection" and paste the URL; the server extracts the node ID (guide article). The desktop server works from the current selection in the desktop app (local-server page). The help pages do not state a numeric frame-size limit.
- **Frame size** (https://developers.figma.com/docs/figma-mcp-server/avoid-large-frames/): "Break screens into smaller parts (like components or logical chunks)"; large selections cause slow tools, errors, and "Incomplete responses due to excessive context"; generate `Card`, `Header`, `Sidebar` individually. Claude Code specific: `get_design_context` can exceed the client's 25000-token MCP output cap; raise `MAX_MCP_OUTPUT_TOKENS` (https://developers.figma.com/docs/figma-mcp-server/mcp-clients-issues/). The FAQ lists a "20kb output response limit per call" for writes.
- **Prompts** (https://developers.figma.com/docs/figma-mcp-server/write-effective-prompts/, https://developers.figma.com/docs/figma-mcp-server/trigger-specific-tools/): "The more specific your prompt, the better the output. Treat it like briefing a teammate." Name the framework, component library, target file path and layout system, e.g. "Generate this using components from src/components/ui", "Add this component to src/components/marketing/PricingCard.tsx". Name a tool explicitly when the agent does not pick it: "Get the variable names and values used in this frame" (`get_variable_defs`).
- **Code Connect** (https://developers.figma.com/docs/figma-mcp-server/code-connect-integration/, https://developers.figma.com/docs/figma-mcp-server/structure-figma-file/): "This is the #1 way to get consistent component reuse in code. Without it, the model is guessing." Output wraps mapped components in `<CodeConnectSnippet>` with imports and snippets; use the in-Figma "Add instructions for MCP" field for patterns and accessibility notes; connect core components first.
- **Design-system rules file** (https://developers.figma.com/docs/figma-mcp-server/add-custom-rules/): write project rules (layout primitives, component naming, file organization, hardcoding policy) into the client's rules file (`CLAUDE.md` for Claude Code); include the required flow ("Run get_design_context first…", validate "for 1:1 look and behavior before marking complete") and "IMPORTANT: If the Figma MCP Server returns a localhost source for an image or SVG, use that source directly".
- **File structure for tokens/variables** (structure-figma-file page): make repeated elements components; apply variables to spacing, color, radius, typography; semantic layer names ("Replace default names (`Frame1268`, `Group5`) with intent-driven ones like `CardContainer`"); auto layout; annotations; dev resource links.

### 5. Reverse direction (code → Figma), first-party

- **Write to canvas** via `use_figma` (remote only, beta): "create and modify native Figma content directly in a Figma Design file" through Plugin API JavaScript, producing "real design structure, such as frames, components, variants, variables, and auto layout" (write-to-canvas page). Announced March 24, 2026 (https://www.figma.com/blog/the-figma-canvas-is-now-open-to-agents/).
- **Code to canvas** via `generate_figma_design` (remote only): the server injects a script into the browser giving a capture toolbar with "Entire screen" or "Select element", turning live UI into editable Figma layers; any seat can create in drafts, editing existing files needs a Full seat (https://developers.figma.com/docs/figma-mcp-server/code-to-canvas/). This is Figma's first-party equivalent of third-party "HTML to design" tools.
- **FigJam / Slides:** `generate_diagram` (Mermaid → FigJam), `get_figjam`, `create_new_file` (Design, FigJam, or Slides); `figma-use-figjam` and `figma-use-slides` skills in the plugin. **Make:** Make files are read through MCP resources; the blog "4 Ways We're Using Our MCP Server at Figma" (June 16, 2026) describes prompting "bring back the preview here into Figma as design layers" (https://www.figma.com/blog/4-ways-were-using-our-mcp-server-at-figma/).

### 6. Limitations Figma lists

- Write to canvas: "20kb output response limit per call", "No asset/image support yet", custom fonts unsupported ("Fonts must be uploaded to your account"), "Components require manual publishing before Code Connect completion", "Beta-level quality — output may need manual review and cleanup" (FAQ; write-to-canvas page).
- Desktop server lacks every tool marked remote-only above, including `download_assets`, `use_figma`, `generate_figma_design`, `generate_diagram`, `search_design_system`; "The desktop server doesn't provide them" (code-to-canvas page).
- Client issues: Claude Code MCP token cap (see 4); Cursor tool-call failures from expired auth tokens, fixed by clearing MCP tokens and re-authenticating (mcp-clients-issues page). MCP prompts (`create_design_system_rules`) and resources (Make) only work on clients that support them (tools page; Make page).
- Rate limits by seat (see 1); View/Collab seats get 6 to 20 calls per month, which effectively rules out non-Dev/Full seats for real use.
